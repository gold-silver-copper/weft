# weft: design

This document explains how weft is built and why: the goals, the core mechanisms, the alternatives that were tried and rejected, and the known limits. The README covers usage.

## 1. Goals

1. **Misuse doesn't compile.** Wherever Rust's type system can express a rule, the rule is a type error, reported by `cargo check` and rust-analyzer, not only by `cargo build`.
2. **No panics.** No code path in the crate panics. Operations that can fail return `Result`/`Option`, and operations that can't fail say so in their types.
3. **No runtime borrow checking.** Access follows Rust's own `&`/`&mut` rules, checked by the compiler. No `RefCell`, no borrow flags.
4. **Relations are first-class.** Typed, valued, many-to-many edges with optional exclusivity, symmetry and cascading.
5. **Stable Rust, no `unsafe`, no dependencies, `no_std` + `alloc`.**

### Non-goals

- **Performance.** Storage uses `BTreeMap`s, chosen for simplicity and deterministic order. Being "slower but correct" is an accepted trade.
- **Parallelism.** Worlds are single-threaded. Nothing here tries to schedule systems concurrently.
- **Runtime extensibility.** Every component, relation and resource type is known at compile time (§3). Adding types at runtime (scripting, hot reload) isn't supported.

## 2. Overview

| concept | role |
|---|---|
| `Entity` | Generational handle (`usize` index, `u32` generation). |
| `Schema` | Compile-time list of the components, relations and resources a `World` can hold. Generated by `schema!`. |
| `Component<S>` | Data on an entity. Generic over the schema, so its hooks can state what they need. |
| `Relation<S>` | Typed edge `source --R--> target` carrying a value of `R`. |
| `World<S>` | Storage plus the operations on it. Reads take `&self`, anything that changes state takes `&mut self`. |
| `Query` / `QueryMut` | Read-only queries over `&World`; borrowing queries over `&mut World`. |
| `Bundle<S, M>` | What `spawn`/`insert` accept. Its failure mode is a type. |
| `Event` / `EntityEvent<S>` | Global and entity-targeted events with observers. Entity events can propagate along any relation. |
| `Schedule<S>` | `FnMut(&mut World<S>)` systems run in order, each with its own change detection. |

Module map: `entity.rs` (allocator), `schema.rs` (schema traits, type-level lists, macros), `component.rs` (`Column`, `Mut`, hooks), `relation.rs` (`Edges`, `Traverse`), `bundle.rs` (bundles and fallibility), `query.rs` (queries, filters, `View`), `world.rs`, `event.rs`, `schedule.rs`.

## 3. The schema

```rust
schema! {
    struct Game {
        components: [mut Pos, mut Vel, Name, Player],
        relations: [ChildOf, Likes],
        resources: [Time, Log],
    }
}
```

The macro generates a unit struct `Game`, then:

- `impl Schema for Game`, whose associated types are heterogeneous lists written as nested pairs:
  - `Columns = (Column<Pos>, (Column<Vel>, (…, ())))`
  - `Relations = (Edges<ChildOf>, (Edges<Likes>, ()))`
  - `Resources = (Time, (Log, ()))`
- One capability impl per entry:
  - `Reads<T>` for every component. It carries a type-level position `type Index` (`Zero`, `Succ<Zero>`, …) and accessors built on the generic `At<N>` trait.
  - `Writes<T>` for components marked `mut`.
  - `Links<R>` for relations.
  - `Owns<T>` for resources.

`macro_rules!` counts positions by nesting `Succ<…>` as it munches the list.

### What this buys

- **Membership is a trait bound.** `world.get::<Name>(e)` requires `Game: Reads<Name>`. A missing type is an E0277 with a custom `#[diagnostic::on_unimplemented]` message that names the schema and says where to add the type.
- **Duplicates are rejected.** Listing a type twice creates conflicting `Reads<T>` impls.
- **No type erasure.** No `TypeId`, `Any` or downcasts are needed for components, relations or resources. Every lookup is a statically resolved field access, so there are no "type didn't match" branches to handle.
- **Resources always exist.** They're fields of the world, initialised with `Default`. `resource::<T>()` returns `&T`.
- **Components are checked against the schema's capabilities.** `Schema::Columns: Columns<Self>` requires `T: Component<Game>` for every listed `T`. If `Player`'s impl needs `S: Writes<Health>` and `Game` lacks it, the error appears at the `schema!` invocation.

### Capabilities as bounds

Code that works with any world names only what it uses:

```rust
impl<S: Writes<Health>> Component<S> for Poisoned { … }
fn physics<S: Borrows<(&'static mut Pos, &'static Vel)>>(w: &mut World<S>) { … }
```

`Reads`, `Writes`, `Links`, `Owns` and `Borrows` form a small capability language. A plugin's signature lists exactly what it touches.

### Mutability lives in the schema

`mut` is declared per schema entry, not on the component type. This fits the capability reading: `Writes<Pos>` means "this world lets you change `Pos` in place". Components without `mut` can still be replaced wholesale with `insert`, which runs hooks. They just can't be changed in place.

## 4. Borrowing queries: the type-level borrow checker

This is the central mechanism.

### Problem

`world.query_mut::<(&mut Pos, &Vel)>()` must hand out `&mut Column<Pos>` and `&Column<Vel>` at the same time. That needs split borrows from a generic container, and it must reject `(&mut Pos, &Pos)` at compile time. Stable Rust has no type inequality (`A ≠ B`), so the rejection can't be written as "all term types are distinct".

### Solution: loans over a list of positions

The columns list doubles as a *type-level description of loan state*. Each slot is one of three kinds:

| slot type | meaning | concrete borrow (`Slot::At<'w>`) |
|---|---|---|
| `Column<T>` | available | `&'w mut Column<T>` |
| `Shared<Column<T>>` | lent out shared | `&'w Column<T>` |
| `Taken` | lent out mutably | `Taken` |

`Loans` maps a whole list to its borrows with a GAT: `<(H, T) as Loans>::At<'w> = (H::At<'w>, T::At<'w>)`. `Columns::refs(&mut self)` produces the initial `At<'w>`, one `&mut` per column, obtained safely by destructuring the nested pairs.

Three traits, indexed by the Peano position from `Reads<T>::Index`, move loans around:

- **`LendMut<N>`** is only implemented when slot `N` is `Column<C>`. It returns `&'w mut C` and turns the slot into `Taken`.
- **`Lend<N>`** is implemented when slot `N` is `Column<C>` or `Shared<C>`. It returns `&'w C` and turns the slot into `Shared<C>`.
- **`Peek<N>`** reads a slot that is `Column<C>` or `Shared<C>`, and is used by `View`.

A query term claims its column from the list and passes the rest on. A tuple claims left to right, threading the list type through `Rest` associated types. The impl for `(A, B, C)` introduces list parameters `L0…L3` tied together by `A: BorrowQuery<S, L0, Rest = L1>`, `B: BorrowQuery<S, L1, Rest = L2>`, and so on.

Consequences:

- **`(&mut Pos, &Pos)` doesn't compile.** After `&mut Pos` the slot is `Taken`, and `Lend<N>` has no impl for `Taken`.
- **`(&mut Pos, &mut Pos)` doesn't compile**, for the same reason with `LendMut`.
- **`(&Pos, &Pos)` compiles.** `Shared` can be lent again.
- **The runtime work matches the proof.** Claiming moves real references out of real tuples. There's no `Option` to take and no "impossible" branch.

These are exactly `&`/`&mut` aliasing rules, but enforced over positions in a list rather than over places in memory.

### Lifetime-free borrow traits

`BorrowQuery<S, L: Loans>` has no lifetime parameter. Lifetimes appear only through GATs (`State<'w>`, `L::At<'w>`, `Item<'a>`). This matters for generic code: a bound like `S: Borrows<Q>` is then a plain trait bound, with no higher-ranked `for<'w>` bounds over projections, which the trait solver handles poorly (see §11).

### `Borrows<Q>` and `QueryData`

- **`Borrows<Q>`** is blanket-implemented for every `S` where `Q: BorrowQuery<S, S::Columns>`. `query_mut` requires only `S: Borrows<Q>`, and `Borrows` carries the claim/fetch methods itself. Schema-generic code therefore needs one bound. It doesn't have to rely on a where clause being implied, which Rust doesn't do for blanket impls.
- **`QueryData`** is a schema-independent trait with `type Item<'a>`. Inside generic code, a projection through the environment bound `<S as Borrows<Q>>::Item` would stay opaque, and closure arguments couldn't be destructured. Because the item type depends only on `Q`, it normalises wherever `Q` is concrete, even when `S` isn't.

### Iteration

A mutable query can't be a standard `Iterator` without `unsafe`, because yielding several `&mut` into the same column requires a lending iterator. `QueryMut` therefore uses internal iteration in two phases:

1. **Select, over `&World`.** Pick the shortest candidate list (from the query's own terms or the filter's), apply the typed `Filter`, and collect the matching entities into a `Vec<Entity>`. Filters (`Added`, `Changed`, `With`, …) need read access to columns the query may borrow mutably, which is why selection happens first.
2. **Fetch, over `&mut World`.** Destructure the world into disjoint field borrows, claim the columns, and for each selected entity call `fetch` and hand the item to the closure.

Read-only `Query` is an ordinary `Copy` handle whose iterator yields `&'w` items directly.

### `View`

`for_each_with` also passes the closure a `View` over everything the query didn't take:
- the leftover loan list, readable via `Peek`
- relations and entities, shared
- resources, mutable
- the deferred-work queue

`view.get::<T>()` compiles only if `T`'s slot isn't `Taken`. This brings back "read other entities while writing this one" (for example, a child reading its parent's `Vel`) with a compile-time check instead of runtime borrow flags.

## 5. Relations

`Relation<S>` declares:
- **`type Arity`**, which is `One` or `Many`. There's deliberately no default, so every relation makes an explicit choice. `world.target::<R>()` requires `R: Relation<S, Arity = One>`.
- **`const SYMMETRIC`**: edges are undirected and share one value, stored under the ordered key `(min, max)`.
- **`const CASCADE`**: despawning a target despawns its sources, recursively.
- **Hooks**: `on_relate` and `on_unrelate`.

Storage, `Edges<R>`:
- `values: BTreeMap<(Entity, Entity), R>`
- `targets` and `sources`: `BTreeMap<Entity, Vec<Entity>>`

The adjacency lists keep insertion order, which makes traversal and query order deterministic. For a symmetric relation, one edge appears in both directions of the adjacency lists.

**Exclusivity is enforced by the world, not the storage.** Relating a `One`-arity source first unrelates its other edges through `World::unrelate`, so their hooks run. For symmetric exclusive relations the target's other edges are removed too.

`Traverse` walks breadth-first with a `seen` set, so it's safe on cycles. `ancestors` follows targets; `descendants` follows sources.

`To(value, target)` pairs a relation with its target inside a bundle. It's a tuple struct because a `.to()` method on a schema-generic trait couldn't infer the schema.

## 6. Bundles and type-level fallibility

`Bundle<S, M>` is implemented for:

- **components**, with marker `IsComponent` and `Error = Infallible`
- **`To<R>`**, with marker `IsRelation` and `Error = NoSuchEntity`
- **tuples of up to 8 bundles**, with marker `(M1, …)` and an `Error` that combines the parts'

The marker parameter `M` exists only to keep these impls from overlapping. A blanket `impl<C: Component<S>> Bundle<S> for C` would conflict with the tuple and `To` impls, because a downstream crate could implement `Component<TheirSchema>` for a tuple. `M` is always inferred.

`Outcome` is implemented for `Infallible` and `NoSuchEntity`:

| | `Infallible` | `NoSuchEntity` |
|---|---|---|
| `Wrap<T>` | `T` | `Result<T, NoSuchEntity>` |
| `Or<B>` | `B` | `NoSuchEntity` |

A tuple's error is `A::Error::Or<B::Error::Or<…::Or<Infallible>>>`. Each part's error converts into it through `Lift`, which is proven per concrete use.

Result: `world.spawn(Pos(0))` returns `Entity`, and `world.spawn((Pos(0), To(ChildOf, p)))` returns `Result<Entity, NoSuchEntity>`. A caller never handles an error that can't happen, and never forgets one that can.

Insertion is **check, then apply**. `check` validates relation targets before anything changes, so a failed spawn creates nothing. `apply` inserts every part. Hooks are queued and run only after the whole bundle, including required components, is in place.

## 7. Hooks, requirements, events and the closure ladder

Each kind of callback uses the most restrictive closure trait that fits how it's called:

| callback | type | reason |
|---|---|---|
| component/relation hooks | `fn` items on the trait impl | stateless, one per type, declared rather than registered |
| observers | `Rc<dyn Fn>` | may be re-entered when an observer triggers the same event; only `Fn` can be re-entered without a runtime borrow flag |
| systems | `Box<dyn FnMut>` | the schedule owns each one and runs it alone, so it may keep state |
| deferred work | `Box<dyn FnOnce>` | runs once |

### Required components

`Component::requires(&mut Requires<S>)` calls `requires.add(value)`. `add` has method-level bounds (`S: Reads<C>, C: Component<S>`), so requirements are checked against the schema's capabilities. They're inserted only if missing, with their own requirements followed. Cycles terminate because an already-present component is skipped.

This isn't `fn requires() -> impl Bundle<S>` because returning a bundle needs a blanket bundle impl over components, which runs into the coherence problem in §6.

### Pending hooks

Pending hooks are stored as `enum Hook { Component(fn, Entity), Relation(fn, Entity, Entity) }`, which are plain function pointers with no allocation. They're drained with `mem::take`, so hooks that insert more things run their own hooks in order.

### Despawn order

1. Collect everything reachable through `CASCADE` (breadth-first with a `seen` set, so cycles are safe), then despawn in reverse: dependents before dependencies.
2. For each entity:
   1. Run relation `on_unrelate` hooks, while both endpoints are intact.
   2. Run every component's `on_remove`, while **all** components are still present. A test caught an earlier version that removed components one by one, so later hooks saw a half-torn-down entity.
   3. Discard whatever the hooks added during teardown, drop the entity's scoped observers, and free the slot.

### Events

- **`Event`** is global. Observers receive `&E`.
- **`EntityEvent<S>`** is triggered on an entity.
  - Observers receive `On<E>`, which knows its entity (no `Option`) and can `stop_propagation()`.
  - `propagate(&World<S>, Entity) -> Option<Entity>` moves the event along any relation. Visited entities are tracked, so cycles end propagation.
  - Entity-scoped observers are removed when their entity despawns.

Observers are stored type-erased: a `TypeId` plus an `Rc<dyn Fn(&mut World<S>, &dyn Any, …)>`. The wrapper downcasts the event and does nothing on a mismatch, so there's no panic path. Before running, the callbacks are cloned into a snapshot, so observers can add or remove observers while they run.

## 8. Change detection

- Each column slot stores `added` and `changed` ticks (`u64`, saturating, so they never wrap).
- `Mut<T>` marks `changed` only through `DerefMut`; reading through it doesn't count. Replacing a value with `insert` also counts as a change.
- `Added<T>` and `Changed<T>` compare against `World::last_run`.
- `Schedule` gives each system its own baseline: `run_tracked` swaps in the system's last-run tick, runs it, flushes deferred work, and advances the tick.
- Outside a schedule, `clear_trackers()` moves the baseline.

## 9. Panic-freedom enforcement

Enforcement has four layers:

1. **`#![forbid(...)]` in `lib.rs`.** Forbid rather than deny, so nothing can be allowed locally:
   - `unsafe_code`
   - `clippy::panic`, `unwrap_used`, `expect_used`, `unreachable`, `todo`, `unimplemented`
   - `indexing_slicing`, `arithmetic_side_effects`, `as_conversions`, `string_slice`, `get_unwrap`
   - `unwrap_in_result`, `panic_in_result_fn`, `exit`
   - `disallowed_macros`, `disallowed_methods`, `disallowed_types`
2. **`clippy.toml`** bans the std APIs that panic on bad input:
   - `assert!` and its variants
   - `Vec::remove`, `swap_remove`, `insert`, `split_off`, `drain`
   - `BTreeMap::range`
   - `Iterator::sum`, `product`, `step_by`
   - `RefCell` and its borrow methods
3. **Design choices that remove the need for panics:**
   - Storage lookups are statically resolved.
   - Claiming loans is total.
   - Interior mutability is only `Cell<Vec<_>>` with `take`/`set`.
   - Entity generations use `checked_add`, and a slot whose generation would wrap is retired rather than reused.
4. **Verification.** One violation of each kind was planted in a scratch module, and all 12 were rejected. A grep of `src/` finds no remaining panicking constructs.

Tests and examples are separate crates and are allowed to assert.

**Out of scope:** running out of memory, stack overflow from unbounded hook recursion, and panics in user hooks, observers and systems.

## 10. Determinism

Nothing iterates in hash order:
- Columns and edge maps are `BTreeMap`s.
- Adjacency lists keep insertion order.
- Observers run in the order they were added, entity-scoped observers before any-entity ones.
- Systems run in the order they were added.
- Despawn order is determined by the cascade order.

## 11. Alternatives considered

| approach | outcome |
|---|---|
| **Per-value `RefCell` on a dynamic `TypeId` world** (the previous version) | Flexible and simple, but aliasing was a runtime panic and every lookup had a downcast failure path. Replaced. |
| **Auto-trait type inequality** (`auto trait Distinct; impl<T> !Distinct for (T, T)`) | Tested on the current nightly: the negative impl disables the auto impl for *all* tuples. Dead end, and nightly-only anyway. |
| **Const `TypeId` comparison** (`const { assert!(TypeId::of::<A>() != TypeId::of::<B>()) }`) | Works on nightly with `const_trait_impl` + `const_cmp`, but it's a post-monomorphization error: invisible to `cargo check` and rust-analyzer. Rejected. |
| **Bitmask of per-schema indices checked in const** | Stable, but also post-monomorphization. Rejected for the same reason. |
| **`BorrowQuery<'w, S, L>` with a lifetime parameter** | Worked for concrete schemas. For generic ones it needed `for<'w>` bounds over GAT projections, and generic plugins couldn't prove disjointness. Replaced by lifetime-free loan families (§4). |
| **`Borrows<Q>::Item`** as the item type | Opaque in generic code (an environment bound shadows the blanket impl). Moved to the schema-independent `QueryData`. |
| **`Option` slots claimed at runtime** | Safe and total, but it only detects conflicts at runtime. The loan types make the same operation a compile-time proof. |
| **Associated-type defaults** (`type Arity = Many`) | Unstable. Arity is required instead, which is also more explicit. |
| **Mutability as an auto trait** (`impl !Mutable for Id {}`) | Users would need `#![feature(negative_impls)]`. Moved mutability into the schema. |

## 12. Known limitations

- **Every type must be listed in a schema.** Each component also needs a one-line `impl<S: Schema> Component<S> for X {}`. A crate can't add component types to someone else's world at runtime.
- **Generic code writes `'static` in `Borrows` bounds**, e.g. `S: Borrows<(&'static mut Pos, &'static Vel)>`. The query's own terms use elided lifetimes, and inference picks `'static`.
- **`View::get` doesn't work in schema-generic code.** The view's loan list is an opaque projection there, so `Peek` can't be proven. The error message ("borrowed mutably by the query") is misleading in this case. Concrete schemas are unaffected.
- **Some error messages are still raw.**
  - `target::<R>()` on a `Many` relation reports `type mismatch resolving … Arity == One`, not a custom message, because `on_unimplemented` doesn't apply to associated-type mismatches.
  - A duplicate schema entry reports a generic conflicting-impl error.
- **Tuples are limited to 8 terms** in queries, filters and bundles (macro-generated).
- **Mutable queries use internal iteration only.** There's no `get(entity)` on `QueryMut`; use `World::get_mut` for a single entity.
- **Performance.** `BTreeMap` lookups everywhere, a `Vec<Entity>` collected per `query_mut`, and a linear scan of observers per trigger.

## 13. Future work

- **Relation joins in queries**, e.g. a term that fetches data from an edge's other end (`Related<ChildOf, &Pos>`). Loans already make "the parent's `Pos`, while the child's `Pos` is taken" expressible as a type question.
- **Borrowing systems.** A `Schedule` entry whose signature declares its borrows (e.g. `S: Borrows<Q>`) could reject conflicting systems when it's built, and later allow safe parallelism.
- **`QueryMut::get`**, via an owned fetch that consumes the claimed state.
- **Better diagnostics** for the cases in §12, e.g. a sealed helper trait on arity so `target` gets an `on_unimplemented` message.
- **Serialization** through an opt-in trait on the schema, walking the column list the same way `Columns` does.

## 14. Testing

- **`tests/weft.rs`** (27 tests): entities, typed fallibility, read and borrowing queries, repeated shared terms, filters, the `View` (reads, resources, deferral), relations (many-to-many, symmetric, exclusive, cascade, traversal), required components (transitive, non-overwriting, cyclic), hook ordering, events and propagation, per-system change detection, and a schema-generic plugin run on two different schemas.
- **Doc tests**: 12 runnable examples, plus 4 `compile_fail` tests pinned to error codes. They cover a missing component, `(&mut Pos, &Pos)`, `View` reading a component the query holds mutably, and `target` on a `Many` relation.
- **Manual compile-failure audit**: nine misuse cases were each compiled and confirmed to fail with the intended message (listed in the README).
- **Both toolchains**: everything is run on stable (1.98.1) and nightly, with clippy at forbid level.
